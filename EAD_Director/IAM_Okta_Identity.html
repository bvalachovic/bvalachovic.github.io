Identity as a Capability, Not a Project

Enterprise Applications Development — position paper on the Okta migration
Prepared July 2026

1. Problem statement (short version)

We are treating the Okta migration as a protocol swap when it is our only realistic chance in a decade to define an enterprise user model. Every custom application we own is an accidental platform: each one maintains its own user table, its own copy of personnel PII, and its own private answer to “who is this person, which offices do they work for, and what may they do there.” Okta will replace the token format and leave that fragmentation intact — at a much higher cost to fix afterward, because forty applications will have been re-wired to a just-in-time profile that is, again, just an email address and a name.

2. Problem statement (full version)

The stated problem. Microsoft’s on-premises federation stack and our Duo MFA integration are approaching support boundaries. IAM and the Okta team have scoped a migration: repoint each relying-party trust from AD FS to Okta, application by application. The Asana plan reflects this — a long, flat list of per-application tasks.

The actual problem. Authentication was never our constraint. Our constraint is that we have no shared definition of a Person, an Office, or the Affiliation between them.

Concretely, today:

  • Each Django and .NET application creates a local user record on assertion and maps it to its own model. The join key is typically email or UPN — both of which change.
  • A staffer who works for two offices exists as two or more unrelated records with no way to reconcile them.
  • Offices re-enter the same PI and PII into several systems during onboarding because no system is authoritative.
  • Pre-employment identity is real and we already model it — a candidate creates an account and applies to posted positions in a separate Django application — but that data dies in that application and is re-keyed when the person is hired.
  • Nobody can answer “what does this person have access to?” or “did separation actually revoke everything?” without polling every application team.

The scoping gap. The current plan contains no task to define a user model, no authoritative source for Person or Office, no identity lifecycle, and no named owner for identity as a shared service. The application teams that own every downstream user model were not consulted. This is Conway’s Law operating exactly as advertised: our authentication architecture is going to mirror our org chart rather than our domain.

The risk if nothing changes. We spend the AD FS budget and finish with the same fragmentation expressed in OIDC instead of WS-Fed, plus forty new integrations to unwind. The security consequence is the sharper one: joiner–mover–leaver events still do not propagate, so separations remain manually reconciled across systems.

The reframe. Identity is not a project with an end date. It is an internal product that IAM owns and every application team consumes — a governed Person/Office/Affiliation model, an authoritative lifecycle with published joiner–mover–leaver events, and SCIM-based provisioning. The AD FS deadline should be the forcing function that funds it, not the reason to skip it.

3. How urgent is the AD FS retirement, really?

Worth being precise here, because the urgency is being used to justify the narrow scope — and it is softer than it sounds.

AD FS has no announced end-of-life date. It is a role within Windows Server, not a separately licensed product with a sunset. Microsoft publishes strong guidance to move from federation to cloud authentication, and an official decommissioning playbook, but “Microsoft is sunsetting AD FS” is not accurate as stated. It is being deprecated by neglect and by advocacy, not by a date.

The real deadline is the operating system underneath it. Windows Server 2016 extended support ends January 12, 2027. If the AD FS farm runs on WS2016, that is a genuine, dated, security-relevant deadline — but the remediation is an OS upgrade to WS2022/2025, which buys years. Migrating identity providers is a choice being made on top of a hosting deadline.

Duo is a similar story. Duo’s AD FS support ended for Windows Server 2012/2012 R2 in October 2023, and the legacy iframe-based prompt reached end of support in March 2024. The current Duo AD FS adapter (v2.x with Universal Prompt) is supported on Windows Server 2016 and later. So Duo is not forcing a move off AD FS — it is forcing a move off old AD FS and the old prompt. If we are already on an unsupported combination, that is an urgent operational problem with a small, well-understood fix.

Questions to verify before conceding the timeline:

  1. What Windows Server version is the AD FS farm on, and what is its actual support end date?
  2. Which Duo adapter version and prompt are we running? Are we already out of support?
  3. Is there a Senate CIO or Sergeant at Arms directive with a hard date, or is the date self-imposed by the project?
  4. Why Okta rather than Entra ID? Microsoft’s documented path off AD FS is Entra. Choosing Okta is a defensible decision, but it should be a decision, not a default.

Bottom line for the interview: do not argue against the migration. Argue that the deadline is bounded, dated, and schedulable — which means the sequencing is negotiable, which means there is room to insert a user-model workstream without moving the date.

4. How I would approach it

Lead with the security argument, not the architecture argument. “We cannot prove that separation revokes access across all systems” moves faster in this building than “our domain model is fragmented.” It is the same problem, stated in the language the sponsors already fund.

Ask for two things, not for a replan. The migration train is moving; asking to stop it loses. Ask for the two things that are nearly free now and nearly impossible later:

  1. An immutable person identifier as the join key. Every application maps to a stable enterprise person_id (Okta sub, or a GUID we mint), never to email or UPN. This is a small per-app change during a migration that is already touching every app, and it preserves every future option.
  2. Affiliation delivered as a claim or SCIM attribute — the person’s set of {office, role, status, effective dates} — rather than each app inferring it locally.

If nothing else in this document lands, those two do.

Build the evidence cheaply, before the interview. Take a one-page Person/Office/Affiliation model to three application teams and ask one question: “what would you delete from your codebase if this existed?” Their answers are the business case, and they are not my opinion.

Use the strangler pattern, not a big-bang model. Each application’s Okta cutover gains one extra step: resolve the local user PK to the enterprise person_id and record the mapping. That lookup table, accumulated app by app, is the seed of the enterprise directory. No app is rewritten; the model emerges from work already scheduled.

Name the capability and give it an owner. “Enterprise Identity Platform,” owned by IAM, with a published, versioned contract (claim set, SCIM schema, event schema) and application teams as named consumers. A capability with a product owner survives the project’s end date; a project does not.

Counter Conway’s Law deliberately. A standing identity working group with one representative per application team, meeting through the migration. The inverse Conway maneuver: change the communication structure to get the architecture you want.

Measure the thing offices actually feel. Number of systems a new staffer’s PII is entered into (target: one). Time from offer to fully provisioned. Time from separation to fully deprovisioned. Count of orphaned accounts. These are onboarding metrics, not identity metrics — which is why they will be believed.

5. Enterprise user model — entity relationship diagram

The design decisions worth defending out loud:

  • PERSON is separate from IDENTITY_ACCOUNT. A human is not a login. People change names, emails, and credentials; the person record must outlive all of them. This is what makes pre-employment identity possible: a candidate is a PERSON with no account yet.
  • AFFILIATION is the center of the model, not PERSON. A person’s relationship to an office is time-bounded, typed (staff, detailee, contractor, intern, fellow, shared staff), and repeatable. A staffer serving two offices has two affiliations, not two identities.
  • Entitlements attach to AFFILIATION, never to PERSON. “Admin users manage personnel for their office” is only expressible if the grant is scoped to the office relationship. This single decision is the one the current plan is on track to get wrong.
  • JOB_APPLICATION references the same PERSON that later becomes an employee. No re-keying, no data death in the recruiting app.
  • APP_LOCAL_PROFILE is modeled honestly. Existing Django and .NET user tables will not disappear. Model them as projections of PERSON with an explicit sync method, and the fragmentation becomes visible and governable rather than invisible and permanent.
  • PERSON_ATTRIBUTE carries classification and authoritative source. This is how “offices enter PII into five systems” stops: every attribute has exactly one system of record.
